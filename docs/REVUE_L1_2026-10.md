## Diff contrôlé

- Schéma : trois champs nullable, pas de défaut ouvrant un accès ; migration créée par migrate dev, sans modification de ligne historique.
- Garde : expiration strictement future, NULL fermé, révocation persistante, médecin courant actif/vérifié, relation entrée↔patient recoupée.
- Services : liste/détail/export/fichiers passent par la portée commune ; mutation de partage et révocation atomiques sous le même verrou.
- Auteurs : session serveur, données client ignorées, rôle de création conservé, aucune fausse attribution historique ; suppression du compte auteur ne modifie pas la preuve dans l'entrée.
- Portée : créer une entrée comme médecin n'ajoute pas de consentement de lecture ; regrant ne ressuscite ni lien supprimé ni lien NULL.
- Compatibilité : endpoint et pagination inchangés ; contrat web enrichi, pas de nouveau parcours frontend. Parent expiresAt = compatibilité conservatrice, jamais guard L1.
- Paiements : aucun changement dans la zone gelée. Chiffrement DMP et filestore conservés ; pas de nouvelle dépendance ni de secret réel.

## Limites concrètes

Le renouvellement des anciens partages est volontairement requis. L'ancien guard est incompatible avec cette reprise fermée : maintenance sans anciens workers et correction en avant documentées. Les audits d'accès/grant restent écrits via le mécanisme existant, hors transaction métier de consentement ; ce lot ne revendique pas une outbox d'audit durable. Une requête déjà autorisée/en cours n'est pas rétroactivement annulée.

L'export préexistant enrichi n'est pas une preuve de conformité FHIR complète. Aucun test d'intrusion externe, appareil physique ou validation clinique/fournisseur obtenu par L1. La recette sept rôles conserve ses cases non exécutées ; les scénarios ajoutés sont un protocole à jouer.
