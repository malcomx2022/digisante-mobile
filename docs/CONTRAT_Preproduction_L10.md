## 2. Candidate et maintenance

Après fusion de la PR, qualifier **le SHA complet de main à déployer** : `CANDIDATE_SHA=<40hex> pnpm preprod:qualify`. Le contrôle lit l'API GitHub : CI `ci.yml` main/push terminée avec succès, `build-and-test` et `e2e` réussis sur le SHA exact. Une CI PR, un ancien SHA ou un job ignoré ne qualifient pas le déploiement. Reprendre le SHA de fusion, qui diffère normalement du head de PR.

Provision initial natif sur l'hôte IONOS partagé via `provision-ionos.sh` (jamais `provision.sh`, ancien VPS 22.04) : `DIGISANTE_ENV=preproduction`, depuis la copie root, dry-run d'abord puis `--apply --only …`, secrets injectés par le coffre de l'opérateur (`infra/deploy/README.md` §1.b). Relire les effets root avant exécution. Pour une cible déjà alimentée, obtenir une sauvegarde complète vérifiée avant migration ; premier bootstrap sur DB vierge déclaré comme tel, puis première sauvegarde après installation. Vérifier héritage audit/L8 sans réécriture et compatibilité des 34 migrations.

Poser et vérifier une maintenance **Nginx** avant le script ; autoriser seulement l'IP de recette de l'opérateur (et l'IP publique de l'hôte, IPv4 et IPv6 si un AAAA la vise, pour `verify_deploy.sh`) pendant les sondes HTTPS : fichier root `snippets/digisante-preprod-maintenance.conf`, inclus par le vhost, posé puis retiré selon `infra/deploy/README.md` §3. La variable `DEPLOY_MAINTENANCE_READY=1` est une **déclaration**, le script ne pose/vérifie pas lui-même Nginx. Suspendre temporairement les crons mutateurs et éviter les sauvegardes concurrentes au déploiement. Consigner leur suspension/reprise ; sauvegarder la crontab actuelle avant modification. `deploy.sh` refuse les modifications Git de l'opérateur, le SHA non exact/hors branche, NODE_ENV autre que production et un `DIGISANTE_ENV` hérité différent de `DEPLOY_ENVIRONMENT`. Hôte partagé : `DEPLOY_ENVIRONMENT` fixe `DIGISANTE_ENV` (profil `digisante_profile`, obligatoire et sans défaut, aussi exigé par `ecosystem.config.cjs`), donc les noms PM2 `digisante-preprod-api/web`, le port de readiness 127.0.0.1:3101 et le checkout `/var/www/digisante-preprod`. Arrêt PM2 API/web **de cet environnement seulement** puis contrôle de l'arrêt **avant** checkout/install/build/migrations ; démarrage homogène, readiness JSON bornée, journal SHA/stade/succès ou échec. Pas de rolling reload pendant migration, pas de rollback automatique et aucune garantie que l'ancien code reste actif en cas d'échec.

```bash
# Maintenance déjà vérifiée. Outillage = deploy.sh de origin/main extrait HORS du checkout (comme les workflows), jamais celui
# du checkout : bash relit le fichier ouvert même après `git switch` (README §3).
# URL du rôle PROPRIÉTAIRE saisie DANS le shell du compte (sudo -u réinitialise l'environnement), jamais en argument.
sudo -u digisante-preprod bash -c 'read -rs -p "MIGRATION_DATABASE_URL (propriétaire, coffre) : " MIGRATION_DATABASE_URL; echo; export MIGRATION_DATABASE_URL \
  && cd /var/www/digisante-preprod && git fetch origin main \
  && M="$(git rev-parse --verify "origin/main^{commit}")" && F="$(mktemp)" \
  && git show "$M:infra/deploy/scripts/deploy.sh" > "$F" \
  && DEPLOY_TOOLING_SHA="$M" DEPLOY_REF=<SHA_COMPLET_QUALIFIE> DEPLOY_ENVIRONMENT=preproduction \
     DEPLOY_MAINTENANCE_READY=1 bash "$F"; rc=$?; rm -f "$F"; exit $rc'
# Prod : compte digisante, /var/www/digisante, DEPLOY_ENVIRONMENT=production (même forme).
# Scripts exécutés par root (B3) au MÊME SHA, depuis la copie root (jamais APP_DIR).
sudo DIGISANTE_ENV=preproduction /usr/local/lib/digisante-preprod/infra/deploy/scripts/install_root_scripts.sh <SHA_COMPLET_QUALIFIE>
# Sondes/configuration ; aucune tâche de notification exécutée par défaut.
sudo DIGISANTE_ENV=preproduction DOMAIN=preprod.digisantemobile.app bash /usr/local/lib/digisante-preprod/infra/deploy/scripts/verify_deploy.sh
```

**B3 — root n'exécute jamais APP_DIR.** Le checkout appartient à l'utilisateur PM2/API de l'environnement : crons, sauvegarde, surveillance, provisioning, Nginx, logrotate et crontab root viennent de la copie root de l'environnement (`/usr/local/lib/digisante-preprod` ; production `/usr/local/lib/digisante`), copie root:root des fichiers de `infra/deploy/root-scripts.list` installée par `DIGISANTE_ENV=preproduction install_root_scripts.sh <SHA>` depuis le miroir nu root `/var/lib/digisante-preprod/ops.git` (URL dans `/etc/digisante-preprod/ops.env`, root 0600, défaut dépôt GitHub public du projet) ; le manifeste inscrit l'environnement et chaque script root refuse la copie d'un autre environnement. SHA complet ancêtre de `origin/main`, blobs du commit, rename atomique par fichier, manifeste `root-scripts.manifest` (SHA + SHA-256) publié en dernier. Chaque script root refuse de tourner depuis un emplacement modifiable par un autre compte ; journaux des tâches root dans `/var/log/digisante-preprod-cron` (root 0750). `deploy.sh` signale (sans échouer) un SHA root installé périmé, `verify_deploy.sh` émet un WARN non bloquant si SHA installé ≠ déployé et un FAIL si la copie est absente/altérée ou si la crontab lance APP_DIR. Amorçage et migration d'un VPS existant : `infra/deploy/README.md` §1 et §3 bis/§5.

Workflow `.github/workflows/preproduction.yml` : manuel, `PREPROD_DEPLOY_ENABLED=true`, SHA qualifié main et maintenance explicitement confirmée ; quatre accès `PREPROD_VPS_*` obligatoires dont fingerprint. Bootstrap lit le script **du SHA qualifié**, pas le script obsolète du checkout. Aucun smoke, paiement ou message automatique. Production : CI requiert **DEPLOY_ENABLED ET DEPLOY_MAINTENANCE_READY** ; conserver les deux désactivées hors fenêtre autorisée, remettre le second à false après la fenêtre. Le workflow n'est pas exécuté par cette livraison.

## 4. Crons et sauvegarde cible

Installer la crontab **préproduction** comme fichier dédié `/etc/cron.d/digisante-preprod` (format cron.d, root:root 0644 ; jamais `crontab <fichier>`, qui remplacerait la crontab root d'ImmiPro/BeninLink) depuis `/usr/local/lib/digisante-preprod/infra/deploy/crontab.preproduction.example` (copie root, B3 — aucun chemin `/var/www`) ; son `DIGISANTE_ENV=preproduction` fixe base `digisante_preprod`, chemins, jeton et API 127.0.0.1:3101 pour backup, tâches et diagnostics. Les horaires restent Africa/Porto-Novo. Secrets/tokens hors crontab ; destinataires et alertes autorisés. Une ligne installée, une invocation manuelle 2xx ou un healthwatch vert ne prouvent pas l'exécution planifiée. Recueillir heures/journaux minimisés et effets uniques : quatre générateurs → notifications, dispatch réel, prune, reconcile, healthwatch et renouvellement TLS. En option, `DIGISANTE_ENV=preproduction VERIFY_JOB_ENVIRONMENT=preproduction ... verify_deploy.sh --run-jobs` **mutera et peut envoyer des messages** : seulement fixtures/destinataires autorisés, jamais en production ; six tâches, résultat distinct de l'observation cron.

Première sauvegarde cible : clé root 0400/0600 conservée hors VPS, filestore présent, DB_NAME dédié. Verrou anti-concurrence ; fichiers temporaires sur le même filesystem. Dump et manifeste DB utilisent **le même snapshot exporté PostgreSQL**, même avec écritures concurrentes. Publication DB/fichiers puis **manifeste en dernier** ; échec avant complétude = pas de trio annoncé/purge des anciens backups. Permissions privées, deux archives chiffrées et empreintes SHA256. Crash brutal peut laisser des archives orphelines : sans manifeste, aucune sauvegarde complète ; examiner sans effacer arbitrairement.

**B4 — le magasin sauvegardé est celui de l'API.** `KYC_STORAGE_DIR` est résolu comme l'API (`scripts/preproduction/filestore-dir.mjs`) : valeur explicite non vide de l'environnement cron, sinon celle du `.env` de l'API (`API_ENV_FILE`, défaut `<APP_DIR>/apps/api/.env` du profil : `/var/www/digisante-preprod/apps/api/.env`) lue comme **données** par `util.parseEnv` (jamais `source`) ; vide ⇒ `storage/kyc`, relatif ⇒ depuis le cwd PM2 de l'API. Répertoire réel exigé (pas de lien). Ce `.env` appartient à l'utilisateur applicatif : sa valeur est **hostile pour root** (B3). Le magasin doit donc appartenir à `APP_USER` (uid résolu par root, jamais 0), sans écriture groupe/autres, et porter un nom simple sans « - » initial ; sinon échec **avant** le dump (une valeur visant `/etc/digisante`, `/root` ou `/` n'est jamais archivée par root). `tar` s'exécute **sous l'identité `APP_USER`** (`sudo -u`, environnement réinitialisé) avec le nom après `--` : aucune option injectée, aucun fichier illisible par l'API lu par root (substitution après contrôle ou fichier root glissé ⇒ échec, rien de publié). Le manifeste porte `files_expected` (identifiants de stockage distincts des `documents` et `kyc_documents`, comptés dans le **même snapshot** que le dump) et `files_missing` (référencés absents de l'index de l'archive) ; `check-backup` et healthwatch refusent `files_count < files_expected` ou `files_missing > 0` (orphelins tolérés, anciens manifestes acceptés comme « complétude non mesurée »). Sauvegarde incomplète : trio publié (la base reste la copie la plus récente), tâche en ÉCHEC, **aucune purge**. Les références d'amorçage (URL seed) ne sont pas comptées.

Le contrôle complet lit les deux archives et vérifie les SHA256, sans déchiffrer/restaurer. Healthwatch utilise une vérification **métadonnées seulement** pour éviter de relire des Go toutes les cinq minutes ; n'atteste pas l'intégrité. Une archive DB seule ne vaut plus sauvegarde complète. Snapshot DB et copie du filestore ne forment **pas une transaction commune** : garder les fixtures au repos lors du premier backup, puis éprouver la restauration réelle cohérente DB+fichiers sur hôte distinct en L11. Les SHA256 détectent l’altération par rapport au manifeste ; un manifeste public non signé ne prouve pas l’authenticité face à un attaquant qui modifie les trois fichiers. Copie hors VPS et récupération de clé à référencer ; 14 jours de backups ne vaut pas politique de conservation des données cliniques/financières.
