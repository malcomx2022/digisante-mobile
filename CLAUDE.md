## 3. Décisions architecturales VERROUILLÉES 🔒

Ces décisions sont définitives. Ne **jamais** les remettre en question, ne jamais générer de code qui les contourne :

1. **PostgreSQL 18.6 natif sur le VPS partagé** (dérogation 13/10 ; PG16 initial) — PAS de Supabase en production. PAS de base managée. Bases + rôles séparés par environnement (`digisante_preprod` / `digisante`).
2. **VPS IONOS partagé** (`srv1.immipro.app`, 31.70.148.167) — PAS de Railway, PAS de Vercel, PAS de déploiement serverless. Hôte partagé avec ImmiPro prod + BeninLink prod/recette (dérogation 13/10 ; Infomaniak distinct initial). I2 « VPS distinct » non conforme, à arbitrer en L11. Domaines `preprod.digisantemobile.app` (préprod) / `digisantemobile.app` + `www` (prod). Chemins et utilisateurs séparés par environnement.
3. **Tout outillage IA** (ex. GBrain de GStack) utilise **sa propre base locale (PGLite)**, strictement séparée de la base de production DigiSanté. Aucun outil de dev ne se connecte à la DB prod.
4. **DOCX uniquement** pour les livrables documentaires (pas de conversion PDF), générés via la lib Node `docx` avec le workflow **build → validate** (et unpack → edit → pack pour les modifications).
5. La logique de paiement FedaPay validée est **gelée** (`/freeze` GStack) : toute modification exige une revue explicite + re-tests des webhooks (HMAC, retry ×5, DLQ, réconciliation cron 02:30).
6. **Frontière des secrets** (gestion des API tierces via l'admin — cf. `docs/PLAN_Gestion_API_Admin.md`) : les secrets d'**infrastructure** (`DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `HEALTH_ENCRYPTION_KEY`, `RECONCILE_TOKEN`) restent en **`.env` UNIQUEMENT** (bootstrap + déchiffrement des secrets DB → pas de dépendance circulaire, pas de point de compromission unique). Les secrets d'**intégration** (FedaPay, Twilio, Daily, Firebase, Resend) peuvent être gérés en base, **chiffrés AES-256 au repos** (clé = `HEALTH_ENCRYPTION_KEY`), **jamais renvoyés en clair** (affichage masqué), avec `.env` en **fallback**. Scope `integrations:write` réservé **SUPER_ADMIN** ; FedaPay reste **§5** (revue + re-tests webhooks).

## 4. Conformité & sécurité (RGPD / APDP — Loi n°2017-20)

À respecter dans **chaque** ligne de code générée :

- **Consentement DMP par entrée (L1)** : médecin **actif et actuellement vérifié** uniquement, lien nominatif patient↔soignant et échéance sur **chaque `ConsentRecord`** (`expiresAt > maintenant`, NULL = refus). `Consent.revokedAt` ferme toute la portée, sans réclamation possible avant ré-octroi explicite. Réclamer un QR ne change que l'entrée désignée ; les lectures/liste/export/fichiers suivent la même portée. Le parent `Consent.expiresAt` n'autorise plus l'accès. Migration sans reprise automatique : le QR courant et l'échéance globale ne prouvent pas le bail historique ; nouvelle réclamation nécessaire. Ré-octroi : renouvelle seulement les liens déjà attribuables ; les NULL restent fermés (`requiresNewShare`). Admin/ASC/diaspora/pharmacie/laboratoire refusés, même avec un QR.
- **Auteur DMP (L1)** : `authorId` et `authorRole` issus de l'acteur authentifié côté serveur, jamais du client. Les anciens auteurs inconnus restent NULL ; pas d'attribution au propriétaire. L'identifiant d'auteur n'a pas de FK vers User pour préserver la preuve après suppression du compte ; il disparaît avec l'entrée médicale. L'auteur n'acquiert aucun droit de lecture supplémentaire. L'export porte un performer uniquement lorsqu'un auteur est connu.
- **Reçus de synchronisation L3** : réponse AES-256-GCM avec clé d'usage dédiée et empreinte HMAC, jamais de corps/réponse clinique en clair dans les reçus. Effet et reçu transactionnels ; statut/rôle/appartenance revalidés avant déchiffrement. Un reçu ne confère aucun droit. L4 chiffre les nouveaux corps sous le coffre ouvert ; sans coffre, ticket minimal et GET de vérification uniquement. L’héritage non migré reste en clair et signalé : lire le contrat L4.
- **Laboratoire L2** : `User.role=LABORATOIRE`, `status=ACTIVE`, `Lab.verifiedAt` requis sous verrou User pour toute lecture clinique/claim/avance/résultat. KYC : structure complète, `NATIONAL_ID` du responsable + `PRACTICE_LICENSE` de la structure ; identité figée à submit, toutes les pièces vérifiées avant APPROVED, nouvelle soumission efface les anciennes coches. Pas de changement de politique KYC médecin. Admin voit identité/pièces uniquement. Suspension : attribution conservée, aucune remise en pool ; réactivation administrative explicite, jamais par KYC. Publication exige PROCESSING et propriétaire, résultat/transition/notifications dans une transaction.
- **Téléconsultation L5** : `join` seul émetteur ; patient/médecin du RDV, rôles/statuts courants et médecin vérifié, ACTIVE/CONFIRMED et début connu < 4 h. Salle Daily relue privée/frappe interdite/deux identités ; jeton `is_owner=false` pour les deux, sans administration, au plus 15 min et borné salle/début DB. Aucune URL/token fictif en secours. SDK officiel : `await load({url})` SANS token, puis `join({url,token})` sur la même instance chargée ; jamais token en URL/DOM/stockage/log ; iframe no-referrer. AUDIO coupe la caméra, CHAT/sortie/expiration coupe caméra/micro puis destroy ; polling 15 s, modes monotones, aucun replay offline. Clôture tente éjection/ban puis DELETE ; panne fournisseur ou bearer externe : expiration comme filet, aucune révocation instantanée absolue promise. Héritage non conforme refusé ; recettes réelles obligatoires. Lire contrat/guide L5 avant modification.
